Test automation quality assessment

ATM Property Testing

An assessment of QE-at-CGI-FI/atm-property-testing, a Playwright suite that tests the hosted ATM at qe-at-cgi-fi.github.io/atm. Its properties were derived with the Antithesis research skill. The evidence comes from browsing the repo with playwright-cli, running the suite locally, and running a 16-mutant fault-injection experiment against a local copy of the ATM.

Assessed 19 Oct 2026 Commit 6d90063 (main, 19 commits) Playwright 1.64.0 Visibility private
Verdict
A stable, readable, well-documented starter suite. It is scenario-based example testing, not yet property-based testing. It caught 11 of 16 injected bugs.

The tests never flaked and run in about 13 seconds. The property catalog behind them is unusually honest about its own gaps. The weak spots are a sign-stripping parser that hides negative values, assertions that only read the screen and so miss state that is never re-rendered, heavy copy-paste, and no CI pipeline.

Fault injection

Which bugs would the suite catch?

I served a copy of the ATM page locally, injected one realistic defect at a time, and ran the full suite on Chromium against each mutant. The unmodified copy passed all 14 tests. A filled square means that spec file failed, so it caught the bug.

spec failed (bug caught) spec passed ✓ killed at least one spec failed ✗ survived every spec passed

The two limit-focused specs (successful-withdrawals-respect-limits and rejected-withdrawals) do most of the work. Three of the five survivors are boundaries that nothing exercises: withdrawing the whole balance, keeping the ATM limit independent of other-ATM usage, and denial because the ATM is out of cash. The other two come from flaws in how the tests observe the app, described below.

Findings

What needs attention

The bill-count parser strips the minus sign

High · masks bugs

Bill counts are read with .replace(/\D/g, ''), which removes every non-digit, the - included. When the ATM shows ×-1, the test reads 1, and toBeGreaterThanOrEqual(0) passes. The test written to catch negative inventory cannot see negative inventory. Mutant M11, which removes the clamp on the €10 refill, survived for this reason.

// admin-configuration-bounds.spec.ts:59 (the same pattern appears in 4 other files)
Number((await page.locator(`#count${d}`).innerText()).replace(/\D/g, ''))
// "×-1"  →  "1"  →  passes the ≥ 0 check

Verified: on mutant M11 the page displays ×-1, and the test's regex turns it into 1. The euro reader /[^\d.-]/g keeps the sign, so the two helpers disagree.

Denials are checked only on the screen, which is not re-rendered after a denial

High · blind spot

The app's denial branches call renderHistory() but not render(). The balance and counters on screen stay stale until the next success. A denial that corrupts state therefore looks fine immediately afterwards. Mutant M09 debits the balance on an ATM-limit denial, and every test still passed.

// mutant M09, after a denied €310 request and then a €10 withdrawal
{ "afterDenial": "€2000",  "afterNext": "€1680" }   // real balance was €1690

Fix: follow each denial with one known-good withdrawal and assert its deltas, or assert against a reference model. The property “denied withdrawal preserves financial state” is the catalog's P1 property, and its oracle needs this.

“Property-based” describes the design method, not the tests

Medium · expectation gap

No generator library is used (fast-check or similar), there is no shrinking, and no operation sequences run against a model. The only generated input is a seeded LCG that always produces the same ten amounts, 90, 220, 20, 190, 260, 80, 160, 160, 100, 50, each on a fresh page. €160 appears twice, and none touches the €300 ATM boundary. The properties are well chosen; the tests check a few handpicked examples of each. The repo's own catalog and README acknowledge this. The project name does not.

Loops inside a single test hide failures and slow diagnosis

Medium · diagnosability

rejected-withdrawals runs 16 scenarios in one test(), and valid-withdrawals runs 10 amounts in one. The first failing scenario aborts the rest. Against mutant M01 the report showed one red test and no indication of how many of the 16 scenarios were affected. There is no test.step anywhere, and traces are recorded only on retry, which happens only in CI.

Copy-pasted helpers and a hardcoded target URL

Medium · maintainability

The URL https://qe-at-cgi-fi.github.io/atm/ is hardcoded 7 times across 6 files, and baseURL is left commented out. readEuroAmount and readBillCount are defined 7 times. Setup flows such as opening Debug and applying limits are reimplemented per file, and there are no fixtures or page objects. To run the mutation experiment I had to rewrite the URL in all six files. A single baseURL from an env var would make local, staging and mutant runs a one-line change.

No pipeline; depends on an unpinned external site

Medium · operability

The repo has no .github/workflows, and package.json has an empty scripts block. The README says the tests “have not necessarily been run”. The system under test is a live GitHub Pages site whose revision the suite does not record, so a change to the ATM repo can break or silently change these tests. Running them offline is impossible.

Smaller issues

Low
  • Non-retrying assertions of the form expect(await readX()) appear 30 times. They work today because the app updates synchronously. Web-first assertions such as toHaveText would survive an async UI.
  • All tests run on three browsers. The logic is browser-independent, so only the input-policy cases (native number-input parsing) benefit from Firefox and WebKit. A Chromium-only logic project would cut runtime by two thirds.
  • valid-withdrawals.spec.ts:52 hardcodes 1900, which assumes the €2000 default balance.
  • The README's install steps include npm init playwright@latest, which re-scaffolds over an existing project, and they require “npm 12.1.0 or newer”.
  • The catalog says non-finite and unusual textual inputs are not covered, but 1e309, 1e308, abc and 1,5 have since been added. The documentation lags the code.

Balance

Strengths to keep, risks to watch

Strengths

  • Rock-solid stability. 252 of 252 executions passed across three browsers and five repeats, with no waits or sleeps.
  • Assertions on relations, not snapshots. Tests compare before and after deltas for balance, both counters and every cassette, which is the right shape for property checks.
  • Smart example choice. The exact-cash cases target the specific greedy-fails-but-knapsack-succeeds branch, and the suite caught both cash-allocation mutants.
  • Excellent analysis artefacts. The SUT analysis, property catalog, relationships and topology notes are explicit about assumptions and open questions, and they correctly conclude that Antithesis is not a fit for this SUT.
  • Readable names and roles. Test names state the property, and buttons are located by accessible role.

Risks

  • False confidence. A green run on admin bounds or denial preservation does not prove those properties (M09, M11).
  • External drift. The SUT lives in a different repo and deploys independently, with no version check.
  • Scaling by copy-paste. Every new property adds another copy of setup and helpers.
  • Learners may take this for property-based testing. In its current form it does not show generators, shrinking or stateful models.
Next steps

Recommended changes, in priority order

  1. Fix the count parser and share one set of helpers
    Create tests/support/atm.ts with readEuro and readCount that keep the sign (/-?\d+/). Re-running M11 should then fail.
    ≈ 30 min
  2. Strengthen the denial oracle
    After each denial, make a €10 withdrawal and assert that the deltas are exactly −10 and +10, or compare against a JS reference model. This kills M09.
    ≈ 1 h
  3. Add the missing boundaries
    Cover withdrawing exactly the balance (M13), other-ATM usage not reducing the ATM allowance (M14), and “ATM out of cash” and “Cannot make exact change” denial reasons (M15).
    ≈ 1 h
  4. Introduce baseURL and fixtures
    baseURL: process.env.ATM_URL ?? 'https://qe-at-cgi-fi.github.io/atm/', plus an atm fixture exposing openDebug(), configure() and withdraw(). This also enables running against a local copy or mutants.
    ≈ 2 h
  5. Make it property-based
    Add fast-check. Use fc.commands to generate sequences of withdraw, refill, configure and set-clock operations, run each against a small reference model, and check every catalog invariant after each step. Log the seed and keep shrinking enabled. Set numRuns low for the UI, or exercise the page's functions directly via page.evaluate for speed.
    ≈ 1 day
  6. One test per scenario
    Turn the rejection and amount loops into for … test() generation, or at least use test.step, so every failing case is reported. Set trace: 'retain-on-failure'.
    ≈ 30 min
  7. Add CI and npm scripts
    Add a GitHub Actions workflow on push, a nightly run against the live site, and "test" and "report" scripts. Keep Firefox and WebKit for input-policy tests only.
    ≈ 1 h
  8. Keep the documentation in step with the code
    Update the catalog's coverage notes and the README install steps, and record the ATM revision or date that each test run targets.
    ≈ 30 min
