Test automation quality assessment

Properties Demo

An assessment of properties-demo, the talk demo for property-based testing of a web UI with Bombadil and Playwright. It tests two local copies of the ATM app: Monday, with known bugs, and Thursday, after the fixes. The evidence comes from reading every suite, rerunning the Playwright walk over several seeds, re-checking the existing Stryker run, and a 16-mutant fault-injection experiment run against both the Playwright walk and the full Bombadil specification.

Assessed 19 Oct 2026 Commit a319457 (agenda2-slides, 5 commits) Playwright 1.63.0 · WebKit Bombadil 0.7.8 · Chrome Stryker 10
Verdict
A clear teaching demo with real generated action sequences, but the random walk starves itself and the Stryker score cannot be trusted. The default Playwright run and a 60-second Bombadil run each caught 5 of 16 injected bugs. Together, over five seeds, they caught 8.

The property names line up across Bombadil and Playwright, which makes the talk's point well. The weak spots are a walk in which only 1 or 2 of about 70 withdrawal attempts succeed, two key properties missing from the Playwright port, a step oracle that reads a screen that is not re-rendered after a denial, and a Stryker setup whose four parallel workers share one mutant switch file.

How it rates as a test automation asset

Fault injection

Which bugs would the suites catch?

I made 16 copies of the Thursday page, each with one realistic defect, in separate folders so no run could see another's mutant. Two of them (M08, M11) put back bugs that Monday really had. I ran the Playwright walk against each with seeds 1 to 5, and the full Bombadil specification once for 60 seconds. Unmodified Thursday passed every run. A filled square means that run failed, so it caught the bug.

run failed (bug caught) run passed ✓ killed caught by the default run (seed 1) ~ other runs caught only by another seed or by Bombadil ✗ survived nothing caught it

The default Playwright seed catches 5 of 16, and five seeds together catch 7. Bombadil catches 5, including M14 through its clock property, which the Playwright walk cannot reach. The two tools overlap on only three mutants (M08, M09, M11, which include both of Monday's real bugs), so running both catches 8. All 8 survivors need a successful withdrawal at or near a boundary, or a specific note inventory. M04, the exact-change bug the catalog confirmed in the original app, survived both tools, even though Bombadil has exactChangeCompleteness.

Mutation harness

What the Stryker run actually measured

Stryker reported 41 killed and 380 survived on Thursday/index.html. The table splits the 421 mutants by the function they changed. Bars share one scale. Green is killed, red is survived.

FunctionKilledSurvivedMutants

Read the score with care. Of the 41 kills, 2 were Playwright crashing on a shared test-results folder and 6 were timeouts waiting for an input that a mutated Debug or Admin toggle had hidden. Of the survivors, 102 are string-literal changes, and 163 are in rendering, clock and admin-panel functions. exactDispense alone has 63 survivors, because the Playwright walk has no property that exercises it. The one finding that matters most is below: the run's per-mutant results are mixed up between workers.

Findings

What needs attention

Stryker's four workers share one mutant switch, so results land on the wrong mutant

High · invalid results

run-mutant.sh writes the active mutant id into Thursday/stryker-active.js. Stryker's command runner runs all four workers in the same sandbox (sandbox-as7SEr appears in every result), so the four workers overwrite one file. A browser can load another worker's mutant. Two mutants show the mix-up directly.

// mutant 159: accRemaining adds other-ATM usage instead of subtracting it
Stryker:  Killed    by atmWithdrawalsRespectAtmLimit   // an ATM-limit property?
Alone:    passed    (seed 1)

// mutant 188: "if (amount > atmRemaining)" → "if (false)"
Stryker:  Survived
Alone:    failed    atmWithdrawalsRespectAtmLimit was violated

Verified by applying each edit to a separate copy of the page and running the same spec with seed 1. Fix: set "concurrency": 1, or let run-mutant.sh copy the app into a fresh mktemp -d folder per run and pass --output to Playwright there. Either keeps the spec unchanged.

The random walk starves: almost every withdrawal is denied

High · weak exploration

Over 8 seeds, each 300-step walk made 65 to 81 withdrawal attempts. Only 1 or 2 succeeded, usually in the first few steps. After that, 28 to 37 attempts per walk were denied with “Account daily limit reached”. Three causes add up. No action moves the clock, so daily counters never reset. Three of the four “withdrawn elsewhere” values are at or above the account limit, which the Thursday clamp turns into “nothing left today”. And the balance is often set to €0 or €100. Properties about successful withdrawals then get one or two chances per run.

// seed 1, Thursday, transactions logged by the app
45 logged · 1 dispensed (€300, step 6)
denied: Account daily limit reached 28 · Insufficient balance 7 · ATM daily limit 9
never reached: ATM out of cash

This explains most survivors in the matrix: M02, M03, M05, M14 and M15 all need a successful withdrawal at or near a boundary. Fix: add a “next day” action (set the clock forward via #cfgClock), weight “withdrawn elsewhere” towards 0, and pick amounts from what is still allowed.

The Playwright port leaves out the two properties that find the real bugs

High · coverage gap

The spec header says it covers “the state invariants and the withdrawal step properties”. Two step properties from Full-test are missing: exactChangeCompleteness and withinLimitWithdrawalNotSpuriouslyDeclined. Both need an independent oracle, and both are about wrongly declined withdrawals. Without them the walk cannot see greedy-only dispensing (M04, the bug the catalog confirmed in the original app), an account limit that is off by one (M05), or a full-balance withdrawal being refused (M15). bindingLimitReasonMatchesTighterLimit is also not ported.

Porting alone is not enough. Bombadil has all three properties and still missed M04, M05 and M15 in 60 seconds (about 1,100 steps each), because its generators rarely set up a note inventory where greedy dispensing fails, or an amount exactly at the remaining allowance or balance. Its one kill through a property Playwright lacks was M07, through bindingLimitReasonMatchesTighterLimit.

Denials are checked on a screen that is not re-rendered after a denial

Medium · blind spot

In withdraw() the denial branches call renderHistory() but not render(). The balance, counters and note counts on screen keep their old values. declinedWithdrawalsDontConsumeCounters compares those screen values before and after, so it passes even when a denial changes state. M09 adds the amount to the account counter on every account-limit denial. The step property never fired. The walk failed later, through accountWithdrawalsRespectAccountLimit, after another action happened to call render().

Fix: read state with page.evaluate('state') for the step properties, or follow each denial with an action that re-renders before comparing. Bombadil reads the same DOM, so its version of this property has the same blind spot.

“Never exceeds” invariants cannot see counters that go the wrong way

Medium · oracle gap

Mutant M02 subtracts the amount from the ATM's daily counter instead of adding it. The counter goes negative, so atmWithdrawn ≤ atmLimit and “remaining ≥ 0” both hold, and the walk passes with every seed. An invariant that the counters never go below zero, or a step property that a successful withdrawal raises both counters by exactly the amount, would catch it. The same applies to M12, where lowering the ATM limit below today's usage is allowed again.

One fixed seed per run

Medium · exploration

Every run uses seed 1 unless SEED is set, so CI and the Stryker run see the same single walk each time. Seeds 2 to 5 caught M07 and M10, which seed 1 missed, and missed M01 and M13 half the time. Seeding is the right design for replay, but the seed should vary between runs and be printed on failure. A few seeds as separate tests would also make the result less dependent on luck.

The full Bombadil spec only runs headful

Medium · operability

With --headless, the Full-test specification stalled on unmodified Thursday about 4 seconds in, right after Bombadil pressed Escape, and logged quiescence timer failed … timed out waiting for response for Runtime.evaluate. It made 76 steps before the watchdog stopped it. Four headless runs in parallel stalled the same way after 13 to 72 steps. Monday-test and Thursday-test replace the default inputs generator because it “presses Escape and Enter, which stall a headless Chrome run”. Full-test keeps the default, so it can only run headful. That is how magic runs it, and it rules out CI.

Fix: reuse the numberInputs generator from Monday-test in Full-test. Until then, treat a stall as “no verdict”, not as a pass. The magic watchdog already does this.

Smaller issues

Low
  • Full-test/README.md describes the original repo: npm test against the live site, npm run test:inspect and a bombadil-output/ folder. None of these exist here; the scripts are test:monday, test:thursday and the inspect:* pair.
  • properties.txt lists 24 names, but the spec exports 22 domain properties plus 4 defaults. bindingLimitReasonMatchesTighterLimit and atmLimitVariedAcrossRun are missing from the list.
  • Playwright-test/playwright.config.ts is headful only, which suits the stage but not CI. The Mutation-test config shows the headless variant.
  • readState returns 0 when a number cannot be read, so a missing or renamed element looks like a valid zero and can satisfy every “≥ 0” invariant.
  • The whole walk is one test(). A failure message includes the last 6 actions and the state, which is good, but there is no test.step per action and no trace on failure.
  • Mutation-test/ is untracked, and the agenda's prompt log mentions magic playwright Tuesday, which the script rejects.

Strengths to keep, risks to watch

Strengths

  • Real generated sequences. Both Bombadil and the Playwright walk generate sequences of withdraw, refill and configure actions and check invariants after every step. This is stateful property-based testing, not a list of examples.
  • Replayable. The Playwright walk is seeded, and a failure prints the property, the last six actions and the full state.
  • One vocabulary across tools. The same property names appear in the catalog, the Bombadil spec, properties.txt and the Playwright test, which makes the comparison easy to present.
  • Monday versus Thursday works as a demo. Monday fails within 2 Bombadil steps and on every Playwright seed; Thursday passes everything.
  • Problems with the tool are handled, not hidden. The custom number-input generator and the magic watchdog both document a Bombadil 0.7.8 limitation in a comment.
  • Boundary-aware generators. Amounts are chosen relative to the current limits and balance (remaining, remaining + 10).

Risks

  • A misleading mutation score. 9.7% from a run with crossed results understates some properties and credits others with kills they did not make.
  • Green does not mean explored. A passing walk has usually made one or two successful withdrawals.
  • Two implementations of every property. The Bombadil and Playwright versions are maintained by hand and have already drifted (3 properties not ported).
  • Stage-only setup. No CI, a headful config and a Bombadil version that stalls under load make it hard to run unattended.
Next steps

Recommended changes, in priority order

  1. Make the Stryker run trustworthy
    Set "concurrency": 1 (about 100 minutes), or give each run its own copy of the app via mktemp -d in run-mutant.sh. Exclude renderClock and string literals in rendering code from mutate so the score speaks about the logic.
    ≈ 1 h
  2. Stop the walk from starving
    Add a “next day” action through #cfgClock, weight “withdrawn elsewhere” towards 0, and draw amounts from [10, min(remaining, balance)] most of the time. Aim for a third of attempts to succeed, and log the success count at the end of each walk.
    ≈ 1 h
  3. Port the missing properties, and generate the states they need
    Bring exactChangeCompleteness, withinLimitWithdrawalNotSpuriouslyDeclined and bindingLimitReasonMatchesTighterLimit over from Full-test with their bounded-knapsack oracle. In both tools, add an action that sets up a greedy-trap inventory (for example 0×€100, 2×€50, 3×€20, 0×€10, then €110), and amounts exactly equal to the remaining allowance and the balance. This targets M04, M05 and M15, which both tools missed.
    ≈ 3 h
  4. Read state, not the stale screen, for step properties
    Use page.evaluate('state') before and after a withdrawal, or force a render first. Add “counters never negative” and “a success raises both counters by exactly the amount”. This targets M02, M09 and M12.
    ≈ 1 h
  5. Vary and report the seed
    Default SEED to the time, print it in the test title and the failure message, and run a handful of seeds as separate tests in CI.
    ≈ 30 min
  6. Add CI
    A GitHub Actions job that runs the Playwright walk headless on Thursday (must pass) and Monday (must fail), plus one serial 60-second Bombadil run.
    ≈ 1 h
  7. Bring the docs in line
    Rewrite Full-test/README.md for the local Monday and Thursday setup, regenerate properties.txt from the spec's exports, and commit Mutation-test/ with its README.
    ≈ 30 min
Method. I read every suite, script, config and README in the repo, and the Stryker log and HTML report from 19 Oct 2026. I reran the Playwright walk headless on WebKit for Thursday with seeds 1–8 and counted the transactions the app logged.
